# Princi v0.1 scope and architecture

This document is the scope boundary for the initial Princi compiler. New
language features and compiler workflows require an explicit update to this
document before implementation.

## User-facing contract

The only v0.1 compiler workflow is:

```text
princi build <source-file>
```

The two accepted source extensions, `.prnc` and `.princi`, are aliases for the
same source language. The extension must not select a different lexer mode,
grammar, type rule, semantic rule, or code-generation behavior.

With no output option, the compiler replaces the source file's extension with
`.exe` and writes the executable beside the source. Thus both
`princi build hello.prnc` and `princi build hello.princi` produce `hello.exe`.
The optional `-o <path>` selects the executable output path, for example:

```text
princi build hello.prnc -o app.exe
```

The v0.1 target is Windows x86-64 only. No other command or target is part of
the user-facing v0.1 compiler contract.

## Language feature boundary

The request defining this scope establishes the file extensions, compilation
workflow, target, and explicit exclusions below. It does not define positive
syntax or semantic features such as declarations, expressions, functions,
primitive types, control flow, or standard-library APIs. This document does not
silently add any of them. A source grammar, type rules, entry-point convention,
and runtime surface are required before language-level compilation can be
implemented as a stable v0.1 feature.

### Explicitly out of scope

- Package manager
- REPL
- Formatter
- Documentation generator
- Debugger
- IDE integration
- Linux and macOS targets
- WebAssembly
- Raw pointers
- Unsafe blocks
- Ownership and borrowing
- Arenas
- Async/await
- Traits
- Interfaces
- Inheritance
- Advanced generics
- Reflection
- Python interoperability

## Compiler pipeline

The planned pipeline is:

```text
source
  → lexer
  → parser
  → AST
  → semantic analysis
  → typed representation
  → LLVM IR
  → Windows object/native code
  → .exe
```

The implementation language is planned to be Rust. LLVM IR is the boundary
between the typed language frontend and Windows-native code generation. The
final artifact is a Windows x86-64 executable.

## Internal module layout

```text
src/
  cli.rs          command parsing and build orchestration
  diagnostics.rs  source locations and user-facing errors
  source.rs       loaded source, line index, locations, and byte spans
  lexer.rs        source text to located tokens
  compiler/
    mod.rs        source loading and compiler entry point
    options.rs    compiler and build options
    pipeline.rs   frontend and backend stage orchestration
    parser.rs     tokens to AST (planned)
    ast.rs        source-oriented syntax tree (planned)
    semantic.rs   name, scope, and language-rule checks (planned)
    types.rs      source types and typed representation (planned)
    codegen.rs    typed representation to LLVM IR and native output (planned)
    runtime.rs    minimal runtime support needed by v0.1 programs (planned)
```

The layers have a one-way flow: diagnostics are available to all frontend
stages; the lexer feeds the parser; the parser builds the AST; semantic analysis
produces a typed representation using the type system; code generation consumes
that representation; runtime support is linked only when required. The CLI
coordinates these stages and chooses input and output paths without changing
the meaning of source files based on their extension.

## Implementation status

The Rust CLI, build-option model, source loading, located diagnostics, tokens,
and lexer are implemented. The pipeline currently lexes source and then stops at
the parser with an explicit incomplete-stage diagnostic. The language grammar
and later frontend, LLVM, and Windows executable-generation stages remain to be
specified and implemented.
