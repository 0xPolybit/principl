# Princi v0.1 scope and architecture

This document is the scope boundary for the initial Princi compiler. New
language features and compiler workflows require an explicit update to this
document before implementation.

## User-facing contract

The only v0.1 compiler workflow is:

```text
princi build <source-file>
```

The two accepted source extensions, `.prnc` and `.princi`, are aliases for the
same source language. The extension must not select a different lexer mode,
grammar, type rule, semantic rule, or code-generation behavior.

With no output option, the compiler replaces the source file's extension with
`.exe` and writes the executable beside the source. Thus both
`princi build hello.prnc` and `princi build hello.princi` produce `hello.exe`.
The optional `-o <path>` selects the executable output path, for example:

```text
princi build hello.prnc -o app.exe
```

The v0.1 target is Windows x86-64 only. No other command or target is part of
the user-facing v0.1 compiler contract.

## Language feature boundary

The parser defines the following source syntax for v0.1. Parsing produces an
AST; accepting syntax does not promise that semantic analysis or native code
generation is complete.

### Declarations and statements

```text
declaration  := function | class | struct | import | extern_block
function     := "fn" identifier parameters ["->" type] block
import       := "import" standard_module
standard_module := "io" | "math"
extern_block := "extern" string_literal "{" {external_function} "}"
external_function := "fn" identifier parameters ["->" ffi_type]
ffi_type     := "Int32" | "Int64" | "Float64" | "Void"
parameters   := "(" [parameter {"," parameter} [","]] ")"
parameter    := identifier ":" type
class        := "class" identifier "{" {field | function | initializer} "}"
struct       := "struct" identifier "{" {field} "}"
field        := identifier ":" type
initializer  := "init" parameters block
block        := "{" {statement} "}"
```

Statements include `let`/`var` declarations with an optional type and/or
initializer, assignment to a name/member/index, nested blocks, `if`/`else`,
`while`, `for identifier in range`, `return` with an optional value, and
expression statements. A variable must have either a type or initializer.
`for` requires a range expression. Semicolons and line breaks may separate
statements. A line break ends a statement when the following token cannot
continue its expression; operators can continue onto the next line.

### Module resolution

The build pipeline resolves top-level imports between parsing and semantic
analysis. v0.1 accepts only the exact built-in module names `io` and `math`:

```princi
import io
import math
```

`io` identifies the built-in I/O module; `print` and `println` remain available
through the global prelude with or without that import. `math` is registered
but currently exports no functions. Imports do not create namespaces, so
qualified calls such as `io.println(...)` are not supported. Repeated imports
are idempotent and resolved once in first-seen order. Unknown names and dotted
module paths receive source-positioned diagnostics.

Resolution is registry-only and does not inspect the filesystem. User-defined
and relative modules, module search roots, and package resolution are deferred.
Only known single-segment identifiers resolve, so path traversal and ambiguous
candidate selection cannot occur. The registry modules have no imports of their
own, and nested imports are rejected, so cyclic imports cannot occur in v0.1.
Module identities use the canonical module name and are independent of `.prnc`
versus `.princi` source files.

### Limited C interoperability

The parser accepts external function declarations only inside `extern "C"`
blocks. An external function has a C linker symbol name, typed parameters, an
optional return type, and no body. Semantic analysis accepts only `Int32`,
`Int64`, and `Float64` for parameters and those types plus `Void` for returns.
`Void` parameters are rejected. These names are C ABI types and cannot be used
in ordinary Princi declarations.

`Int32` and `Int64` map to Princi `Int`; `Float64` maps to Princi `Float`.
`Int32` arguments are checked against the signed 32-bit range before the call,
and C `Int32` returns are sign-extended to Princi `Int`. `Int64` maps directly
to C `int64_t`; `Float64` maps to C `double`. Managed values (`String`, class,
and List), structs, booleans, generic types, and `Void` arguments are unsafe and
rejected. Calls are direct and non-variadic. External names must be ASCII C
identifiers and cannot collide with compiler/runtime symbols.

The backend emits LLVM `ccc` declarations and calls. LLVM defines `ccc` as the
target C calling convention, so the explicit Windows x86-64 triple selects the
Windows x64 C ABI. The current linker step resolves the generated object and
Windows C runtime only; additional user libraries or C object files cannot be
passed through the v0.1 CLI. Raw pointers, `repr(C)` aggregates, callbacks,
manual memory operations, pinning, C varargs, and other calling conventions
remain out of scope.

### Expressions and precedence

Expressions include primitive literals, identifiers, `self`, list literals,
named-field construction (`Point { x: 1, y: 2 }`), calls, member access,
indexing, parenthesized expressions, unary `+`/`-`/`!`, binary expressions, and
the `..` range expression. Assignment is a statement, not an expression.

The parser uses a Pratt expression parser. Binary operators associate
left-to-right. Ranges are non-associative; parentheses can group a range. From
lowest to highest precedence:

| Precedence | Operators |
| --- | --- |
| 1 | `..` (non-associative) |
| 2 | `||` |
| 3 | `&&` |
| 4 | `==`, `!=` |
| 5 | `<`, `<=`, `>`, `>=` |
| 6 | `+`, `-` |
| 7 | `*`, `/`, `%` |
| 8 | unary `+`, `-`, `!` |
| 9 | calls, member access, indexing |

Object construction uses `Type { field: value }`. In `if`/`while` conditions
and range bounds, an immediately following `{` starts the control-flow body;
parenthesize an object construction in those positions to disambiguate it.

The parser preserves source spans on AST nodes and accumulates diagnostics.
Recovery synchronizes at statement separators and later-line statement,
member, or declaration starts while leaving enclosing closing braces available
to their owning parser.

### Static typing

The primitive types are `Int`, `Float`, `Bool`, `String`, and `Void`. Class and
struct names introduce distinct nominal types. Function/method return types
default to `Void`; parameters and fields require explicit, non-`Void` types.
Local declarations may infer from their initializer, but there is no
cross-declaration or Hindley-Milner inference. `var` bindings are mutable;
`let`, parameters, and `for` bindings are immutable. Duplicate declarations
are rejected within a scope; a nested scope may shadow an outer local.
`let` requires an initializer; `var` may be declared with a type and initialized
later. A local cannot be read until it is definitely initialized. Assignments
in both arms of an `if` establish initialization after the branch; assignments
inside `while` and `for` bodies do not, because those loops may execute zero
times.

There are no implicit numeric conversions. `+`, `-`, `*`, and `/` accept two
matching numeric types; `+` also concatenates strings. `%` accepts integers.
Comparisons accept matching numeric types; equality accepts matching primitive
types. Boolean operators and `if`/`while` conditions require `Bool`. `List<T>`
is the sole generic source type in v0.1 and requires exactly one non-`Void`
element type. Other generic types are rejected. List literals are homogeneous
and infer their element type when nonempty; empty lists need an expected
`List<T>` type. No common-type or numeric-promotion inference is performed, so
mixed element types are rejected. List element types may themselves be lists,
classes, structs, or primitives. Index expressions require an `Int`; runtime
checks reject negative and out-of-range indexes. `.length` is a read-only `Int`
property, and `.add(value)` accepts exactly one element of type `T` and returns
`Void`.

Lists are heap-backed reference values. Assignment, parameter passing, and
returns copy the handle, so aliases observe the same content changes. `let`
protects the binding from reassignment but allows mutation of list elements and
`.add`. Indexed writes require a mutable list binding where applicable; a
field nested beneath a struct value read from an indexed list must be copied,
updated, and assigned back as a whole element. The runtime stores elements in
type-sized byte slots and copies values in and out; this representation is
private to the compiler/runtime ABI. The v0.1 managed-memory model below
specifies how list and other managed storage is reclaimed. A range expression
has matching numeric bounds, but native `for` loops in v0.1 specifically
require `Int` bounds and bind an immutable `Int` loop variable. The end bound
is exclusive.

Calls check arity and argument types. An omitted function return annotation
means `Void`; return statements must match it. `print` is a built-in accepting
one non-`Void` value; `println` accepts the same types and appends a line break.
Named field construction requires every declared field once with a compatible
value and initializes those fields directly. `Type(args)` uses a declared
`init` signature or, when no initializer exists, a positional signature in
field declaration order. Fields and methods have no visibility modifiers in
v0.1; all are public/module-visible under this temporary rule. Imports are
resolved against the built-in registry described in Module resolution.

Semantic analysis builds global function/type symbols, per-type field and
method tables, and lexical local scopes. It resolves type names before checking
bodies so declarations can refer to types declared later in the file. It
retains inferred local and expression types in the typed-program result.
Semantic diagnostics carry the source path, line, column, and span; the build
pipeline stops before later stages when any semantic diagnostic is present.

Struct construction uses all fields in declaration order for `Type(args)` or
every field exactly once for `Type { field: value }`; struct declarations do
not have `init` constructors or methods. Recursive struct fields by value are
rejected because they cannot have a finite layout.

### Native backend boundary

Native generation supports top-level functions, parameters, `Int`, `Float`,
`Bool`, `String`, `List<T>`, local `let`/`var`, assignment, arithmetic and
comparison, boolean operators, `if`/`else`, `while`, integer range loops,
returns, direct function calls, recursion, classes, field-only structs, and
`print`/`println`.
Class support includes instance fields, constructors, and instance methods.
Struct support includes fields, positional and named construction, field
access, mutation through a mutable binding, function parameters, and return
values. `main` is required, takes no parameters, and returns `Void` or `Int`; an
`Int` result becomes the process exit status. A non-`Void` function must return
on every control-flow path.

Native `Int` uses signed 64-bit values and wraps on arithmetic overflow. The
backend does not implicitly convert numeric types. String `+` concatenates,
string equality compares contents, and the print built-ins select a primitive
formatter from the expression's checked type. Class instances are represented
with nominal class types in the frontend and as opaque pointers in LLVM. The
backend lays each class out as a metadata pointer followed by fields in
declaration order. The metadata pointer targets an internal type descriptor
so richer runtime metadata can be added without changing source syntax or
frontend types. Constructors allocate zero-initialized storage; methods use
static dispatch through class-qualified symbols with a hidden `self` pointer.
There are no vtables or virtual calls.

Structs are nominal value types lowered to LLVM aggregates with fields in
declaration order and no object header or allocation. Construction creates an
aggregate directly. Local initialization and assignment, function arguments,
and return values copy the aggregate by value. Reading a field extracts it from
the aggregate; mutation stores through the mutable value's address. `let`
bindings and function parameters are immutable, so their fields cannot be
mutated. A class-valued struct field copies the class pointer and therefore
continues to refer to the same class instance. Struct methods and `init`
constructors are rejected in v0.1.

Class methods and fields and struct fields are public/module-visible because
visibility syntax does not exist in v0.1. Classes support one optional
`init`, no inheritance, and no method overloading.

Lists support homogeneous and inferred literals, typed empty literals,
`.length`, indexed reads and writes, and `.add(value)`. The runtime checks
negative and past-end indexes. Imports resolve only the built-in `io` and
`math` names; restricted `extern "C"` declarations accept `Int32`, `Int64`,
`Float64`, and `Void` returns under the C ABI rules above.

### Managed memory v0.1

`String`, `Class`, and `List<T>` are distinct managed-reference variants in
the compiler type system. They lower to opaque LLVM pointers. Structs remain
inline value types and are not themselves managed references, though their
fields may contain managed references. There is no raw-pointer type in v0.1.
Strings use NUL-terminated UTF-8 storage; embedded NUL bytes and `\0` escapes
are rejected so printing, concatenation, and equality preserve the same value.

The private runtime ABI uses a process-lifetime heap registry backed by the
Windows C heap. Dynamic string concatenation results, class instances, list
headers, and list backing buffers are registered by `managed_alloc`,
`managed_calloc`, and `managed_grow`. String literals are immutable module
constants and require no allocation. The generated entry wrapper releases all
registered blocks after Princi `main` returns; runtime error paths also
release them before exiting. Princi source has no allocate or free operation.

The heap registry does not reclaim unreachable objects during execution.
Temporaries, cycles, strings, lists, and superseded list buffers remain
allocated until the program exits. This conservative lifetime avoids dangling
references without reference counting or root scanning, but long-running
allocation-heavy programs can grow in memory. The allocation boundary is kept
private so a future tracing collector, including a generational or concurrent
design, can replace it without changing source syntax. There are no finalizers,
pinning, borrowing, ownership, or user-controlled arenas in v0.1.

## Compiler pipeline

The compiler pipeline is:

```text
source
  → lexer
  → parser
  → AST
  → built-in module resolution
  → semantic analysis
  → typed representation
  → LLVM IR
  → Windows object/native code
  → .exe
```

The implementation language is Rust. The backend lowers the typed program to
LLVM IR. Clang's LLVM IR reader parses and verifies it while emitting a COFF
object for the explicit x86_64-w64-windows-gnu target. MinGW-w64 GCC links the
object and Windows C runtime into the final Windows x86-64 executable.
Temporary IR and object files are removed after each build. Development builds
can set PRINCI_KEEP_INTERMEDIATES=1 to keep them and print their directory.

## Internal module layout

```text
src/
  cli.rs          command parsing and build orchestration
  diagnostics.rs  source locations and user-facing errors
  source.rs       loaded source, line index, locations, and byte spans
  lexer.rs        source text to located tokens
  ast.rs          source-oriented syntax tree with spans
  parser.rs       tokens to AST, precedence, and error recovery
  modules.rs      deterministic resolution of built-in imports
  ffi.rs          restricted C ABI types and Princi boundary mapping
  compiler/
    mod.rs        source loading and compiler entry point
    options.rs    compiler and build options
    pipeline.rs   frontend and backend stage orchestration
  semantic.rs     name, scope, and language-rule checks
  types.rs        source types and typed representation
  codegen.rs      LLVM lowering, verification, object generation, and linking
  codegen/
    llvm.rs       procedural/class/struct lowering and Windows toolchain bridge
  runtime.rs      runtime ABI facade
  runtime/
    windows_x86_64.rs  Windows print, managed allocation, and process ABI
```

The layers have a one-way flow: diagnostics are available to all frontend
stages; the lexer feeds the parser; the parser builds the AST; module resolution
records the canonical standard modules; semantic analysis produces a typed
representation using the type system; code generation consumes that
representation and includes the Windows ABI helpers in generated LLVM IR.
MinGW GCC resolves their C runtime calls automatically during the normal build.
The CLI coordinates these stages and chooses input and output paths without
changing the meaning of source files based on their extension.

## Implementation status

The Rust CLI, build-option model, source loading, located diagnostics, tokens,
lexer, AST, parser, built-in module resolution, restricted C FFI, type system,
semantic analysis, LLVM lowering, generic print/println built-ins, class instances, lists, process-lifetime managed
memory, target runtime helpers, and Windows executable generation are
implemented. The backend requires LLVM/Clang 15 or
newer with LLVM IR input support and the X86 target, plus x86-64 MinGW-w64 GCC.
The target triple is specified explicitly; it does not depend on host defaults.
