# PrinciPL v0.2 scope

This is the canonical scope boundary for PrinciPL v0.2 development. Some
features below are implemented and others remain planned; their headings state
the current status. The released compiler remains v0.1.0. Implementation work
must stay within this document and preserve the v0.1 contract below.

## v0.1 functionality today

The current compiler is a Rust application with a single user-facing workflow:

```text
princi build <source.prnc|source.princi> [-o output.exe]
```

`.prnc` and `.princi` are interchangeable extensions for the same language.
The default output is an `.exe` beside the input. The only target is Windows
x86-64; native builds use LLVM/Clang to verify LLVM IR and emit a Windows COFF
object, then MinGW-w64 GCC to link the executable.

Implemented language features include statically typed `Int`, `Float`, `Bool`,
`String`, and `Void`; local `let` and `var`; functions, recursion, and control
flow; classes with fields, constructors, and statically dispatched methods;
field-only structs with value semantics; and the built-in `List<T>` with
homogeneous elements, indexing, mutation, `.length`, and `.add`. The compiler
also supports the built-in `io` and `math` import names and a restricted
`extern "C"` boundary for `Int32`, `Int64`, `Float64`, and `Void` returns.

### Generic-function monomorphization implemented

The repository implements monomorphized generic functions as a v0.2 feature.
Generic declarations carry distinct type-parameter identities, and the typed
program records concrete type arguments and specialized call signatures. Calls
may provide explicit type arguments or infer them from argument types when
every parameter has one unambiguous concrete substitution. The compiler emits
only used specializations, reuses an existing specialization for repeat calls,
and names specializations deterministically. Same-type generic recursion works.
Recursion that keeps expanding a type, or a program requiring more than 512
specializations, receives a diagnostic rather than looping indefinitely.
Inference uses call arguments, not an expected result type; an unconstrained
parameter therefore requires an explicit argument (or produces an inference
diagnostic).

Native generic functions currently support concrete primitives, class and
struct values/references, generic enum values, and nested built-in `List<T>`
types. Generic classes and structs are specialized for concrete instances
used by a program.
Generic classes have distinct managed-reference layouts with runtime metadata;
generic structs have distinct inline LLVM aggregate layouts and retain value
semantics. Constructors support explicit type arguments and infer arguments
from constructor parameter types when all parameters can be determined. Generic
methods can use their enclosing class's parameters. Method-level generic
parameters are not yet lowered. `List<T>` keeps its existing native runtime
representation. Generic enums specialize to inline LLVM aggregates. This is
partial v0.2 progress, not a claim that the full interface, trait, or
pattern-matching scope below is complete.

The compiler pipeline and managed-memory behavior are documented in
[`v0.1-scope.md`](v0.1-scope.md). In particular, v0.1 managed storage is
retained for the process lifetime and released when the generated program
exits; it is not a tracing garbage collector.

## v0.2 additions

### General generics and specialization

Generalize type parameter syntax across functions, methods, classes, structs,
and enums. Type arguments may be nested, so types such as `List<Box<Int>>` are
expressible. The existing `List<T>` syntax and behavior remain supported.

```princi
fn identity<T>(value: T) -> T {
    return value
}

struct Box<T> {
    value: T
}

enum Option<T> {
    Some(T),
    None
}
```

Generic function arguments are inferred when call arguments determine one
unambiguous substitution; callers may write explicit type arguments when
inference is insufficient. Generic class, struct, and enum arguments are
specified at type use and construction sites. The compiler specializes generic
code at compile time (monomorphization) for each concrete type-argument set.
There is no runtime generic reflection or user-controlled specialization
syntax. Generic function specialization is implemented for the concrete types
listed above. Generic class and struct layouts are specialized per concrete
instance, and their constructors and class methods are emitted on demand.
Generic methods may use type parameters declared on their enclosing class;
method-level generic parameters remain outside this implementation.

### Generic constraints

Top-level generic functions, classes, and structs may declare interface and/or
trait bounds inline. Separate multiple bounds with `+`:

```princi
trait Named { fn name() -> String }
interface Drawable { fn draw() }

fn describe<T: Named + Drawable>(value: T) -> String {
    value.draw()
    return value.name()
}

class User implements Named, Drawable {
    fn name() -> String { return "Ada" }
    fn draw() { println("drawing") }
}

class Repository<T: Named> {
    value: T
}

struct Holder<T: Named> {
    value: T
}

fn main() {
    let user = User()
    println(describe(user))
    let repository = Repository<User>(user)
    let holder = Holder<User> { value: user }
}
```

Each bound must name a declared interface or trait and cannot have generic type
arguments. Explicit and inferred generic function arguments, plus generic class
and struct instances, are checked against every listed contract before native
specialization. A type parameter exposes only methods declared by its bounds;
if multiple bounds declare the same method, their signatures must be identical.
An interface bound is satisfied by a conforming class. A trait bound is
satisfied by a conforming class or struct. A type parameter passed onward must
already carry the required bound. Failed checks produce a compact diagnostic,
for example `type Int does not satisfy required trait 'Named'`. Method-level
generic parameters remain unsupported.

Traits and interfaces themselves are not generic. Associated types, negative
bounds, conditional implementations, and automatic conversions from bounds are
not supported.

### Interfaces and runtime dispatch

An interface declares a set of instance-method signatures. It has no stored
fields, constructors, default method bodies, associated types, or generic
methods. Classes explicitly declare the interfaces they implement and must
provide compatible methods. A class may implement more than one interface.

```princi
interface Printable {
    fn text() -> String
}

class User implements Printable {
    name: String

    init(name: String) {
        self.name = name
    }

    fn text() -> String {
        return self.name
    }
}

fn show(value: Printable) {
    println(value.text())
}
```

In v0.2, only class instances can be stored as interface-typed values. A
conforming class converts to an interface view in locals, parameters, returns,
class/struct fields, and `List<Interface>` values. Calls through that view use a
runtime pair of the object reference and a compiler-generated per-class,
per-interface method table. Calls on a concrete class keep v0.1 static
dispatch. Structs do not convert to interface values in v0.2. Interfaces are
not a class inheritance mechanism.

### Traits and trait implementations

An **interface** is a pure behavioral contract: it declares required method
signatures and cannot provide bodies. A **trait** is a behavioral contract that
may provide default method implementations. Traits have no fields, constructors,
or generic methods. A class or struct declares implementations with the same
`implements` clause used by classes for interfaces:

```princi
trait Named {
    fn name() -> String

    fn describe() {
        println(self.name())
    }
}

class User implements Named {
    value: String

    init(value: String) {
        self.value = value
    }

    fn name() -> String {
        return self.value
    }
}
```

The type must implement each abstract method with a compatible signature. It
may override a default with its own method. If two implemented traits supply a
default with the same name and the type does not implement that method
explicitly, compilation reports an ambiguity; there is no automatic
precedence. Concrete calls use static dispatch. Trait-typed values use the same
internal `{data, method-table}` representation and runtime dispatch mechanism as
interface-typed values. Classes keep reference semantics. Converting a struct
to a trait value boxes a copy in process-lifetime managed storage, so the view
does not observe later changes to the source struct. Struct methods are
currently supported only on structs that implement a trait, and have read-only
`self` in this implementation.

Trait definitions are non-generic. Trait bounds can constrain generic
functions, classes, and structs. Associated types, blanket implementations,
overlapping implementations, and specialization rules are outside this scope.

### Algebraic enums (implemented construction, layout, and matching subset)

Enums add named variants with optional positional payloads. Enums may be
generic. The parser, semantic analyzer, and native backend support declarations,
generic type references, and variant construction. Nullary variants use
`Direction.North`; payload variants use `NetworkState.Failed("offline")`; a
generic variant uses explicit concrete arguments such as
`Result<Int, String>.Ok(42)`. Generic enum arguments are not inferred from
variant payloads.

```princi
enum Direction {
    North
    South
}

enum NetworkState {
    Connected
    Failed(String)
}

enum Maybe<T> {
    Some(T)
    None
}

enum Result<T, E> {
    Ok(T)
    Err(E)
}

fn main() {
    let direction = Direction.North
    let failure = NetworkState.Failed("offline")
    let result = Result<Int, String>.Ok(42)
}
```

The current LLVM representation is an inline aggregate with an `i32` tag and
one typed payload aggregate per variant. Struct and nested enum payloads copy
by value. String, List, and class-reference payloads retain their existing
managed-reference behavior. The layout is compiler-internal and is not a C ABI
layout. Duplicate variants, unknown variants, incorrect payload arity or type,
and recursive inline layouts produce semantic diagnostics.

Enum values can be constructed, stored, passed to functions, returned, nested
in generic values, and inspected with `match`. `Maybe<T>` and `Result<T, E>`
are ordinary user-declared enums, not built-in prelude types.

### Pattern matching (implemented subset)

`match` is an expression; it can also be used as a statement when its result is
`Void`. Arms accept enum variant names, positional payload patterns, immutable
bindings, `_`, and primitive literal patterns for `Int`, `Float`, `Bool`, and
`String`. Payload patterns can be nested. Bare names matching nullary enum
variants select them; payload variants require parentheses, even when the
payload pattern is `_`. Other lowercase names bind the whole value, while an
unknown uppercase name is diagnosed as a likely misspelled variant.

All expression arms must produce compatible types. Block arms have type
`Void`. A match must cover every enum variant, or have a wildcard/binding arm;
`Bool` matches are exhaustive when both boolean literals are present. Other
primitive matches require a catch-all. The checker diagnoses duplicate and
shadowed patterns. For nested payloads it conservatively requires a catch-all
unless a payload pattern is irrefutable. Every arm has a lexical scope, and
pattern bindings are immutable and do not escape that arm.

Simple enum matches lower to LLVM switches on the enum discriminant. Nested
patterns and literal patterns use conditional comparisons. Match guards,
array/list patterns, struct destructuring, and range patterns are outside the
v0.2 subset.

### `Result<T, E>` and `?` (planned)

`Result<T, E>` is not predeclared; a program may declare it as a generic enum.
Postfix `?` error propagation is planned, but is not parsed or lowered yet. The
planned operator will unwrap `Ok(U)` to `U` and return `Err(E)` from the current
function, without implicit error conversion. The process entry point remains
`fn main() -> Void` or `fn main() -> Int`.

## v0.2 compiler architecture

The v0.1 frontend and Windows native pipeline remain the foundation. The v0.2
frontend includes generic constraint checking, interface/trait conformance,
generic enum construction/layout, and match exhaustiveness analysis:

```text
.prnc / .princi
        ↓
      source
        ↓
      lexer
        ↓
      parser
        ↓
       AST
        ↓
 built-in module resolution
        ↓
 semantic and type analysis
 (bounds, implementations, exhaustiveness)
        ↓
 generic specialization
        ↓
 typed representation
        ↓
     LLVM IR
        ↓
 Windows x86-64 COFF object
        ↓
 MinGW-w64 linker and runtime
        ↓
       .exe
```

Generic specializations are compile-time artifacts. Enum tags/payloads and
interface dispatch tables are compiler-managed implementation details, not
user-defined layouts. Existing strings, classes, lists, and other managed
references continue to use the private runtime allocation boundary. This scope
does not require changing the v0.1 process-lifetime allocation model.

The existing Rust implementation is split across these modules:

| Concern | v0.1 implementation |
| --- | --- |
| CLI and build configuration | `src/cli.rs`, `src/compiler/options.rs`, and `src/compiler/pipeline.rs` |
| Source locations and diagnostics | `src/source.rs` and `src/diagnostics.rs` |
| Frontend | `src/lexer.rs`, `src/parser.rs`, and `src/ast.rs` |
| Imports and C ABI boundary | `src/modules.rs` and `src/ffi.rs` |
| Semantic analysis and types | `src/semantic.rs` and `src/types.rs` |
| LLVM generation and native toolchain | `src/codegen/llvm.rs` |
| Runtime ABI | `src/runtime.rs` and `src/runtime/windows_x86_64.rs` |

The v0.1-compatible type model distinguishes concrete primitive, class, and
struct types, generic type parameters, and generic instances. `List<T>` is the
only generic instance with complete v0.1 native support; the repository's
initial generic frontend work is documented above. Class instances are managed
references with an internal metadata pointer followed by fields in declaration
order. Structs are LLVM aggregates copied by value. Lists are opaque managed
references with homogeneous element storage. Imports resolve only the built-in
`io` and `math` names, and `extern "C"` accepts only the documented primitive
ABI types.

## Compatibility expectations

- Every v0.1 language feature and its behavior remain supported; the existing
  v0.1 conformance and native integration programs must continue to compile and
  run with the same observable results.
- `.prnc` and `.princi` remain exact aliases. Neither extension may select a
  different parser, type rule, or backend path.
- The user-facing workflow remains `princi build <source-file>` with optional
  `-o <output.exe>`. There are no new top-level CLI commands in v0.2.
- Windows x86-64 remains the only target. The object format, linker pipeline,
  and toolchain diagnostics remain Windows-specific.
- Existing numeric rules, class reference behavior, struct value behavior,
  List behavior, module registry, C FFI boundary, and managed-memory model do
  not change as a side effect of adding the listed features.
- New syntax words should be contextual so existing v0.1 identifiers remain
  usable. `Result<T, E>` is an ordinary user-declared generic enum, not a
  compiler-reserved or predeclared type.
- New errors remain source-positioned compiler diagnostics and failures return
  a non-zero exit code without exposing internal panics.

## Explicitly outside v0.2

These are not v0.2 features. Listing them here marks the boundary, not a release
commitment or a promise that they are the next roadmap items:

- Class inheritance, virtual class inheritance, and virtual class methods.
- Raw pointers, unsafe blocks, manual memory management, ownership/borrowing,
  and user-controlled arenas.
- Async/await and threading language syntax.
- Package management and remote dependency resolution.
- Linux/macOS compilation and WebAssembly.
- Decorators, reflection, operator overloading, and macros.
- Associated types, higher-kinded types, variadic generics, user-defined
  specialization syntax, and user-defined memory layouts.

## Future functionality

Anything beyond the v0.2 additions above remains future work. Potential areas
for later design include broader platform support, richer runtime memory
management, package/module ecosystems, and additional generic abstractions.
None of those capabilities should be described as available until they are
implemented, tested, and documented against the compiler.
