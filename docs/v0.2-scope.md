# PrinciPL v0.2 scope

This is the canonical scope boundary for the proposed PrinciPL v0.2 release.
It describes planned language and compiler behavior; it does not mean that
these features are implemented today. The released compiler remains v0.1.0.
Implementation work must stay within this document and must preserve the v0.1
contract below.

## v0.1 functionality today

The current compiler is a Rust application with a single user-facing workflow:

```text
princi build <source.prnc|source.princi> [-o output.exe]
```

`.prnc` and `.princi` are interchangeable extensions for the same language.
The default output is an `.exe` beside the input. The only target is Windows
x86-64; native builds use LLVM/Clang to verify LLVM IR and emit a Windows COFF
object, then MinGW-w64 GCC to link the executable.

Implemented language features include statically typed `Int`, `Float`, `Bool`,
`String`, and `Void`; local `let` and `var`; functions, recursion, and control
flow; classes with fields, constructors, and statically dispatched methods;
field-only structs with value semantics; and the built-in `List<T>` with
homogeneous elements, indexing, mutation, `.length`, and `.add`. The compiler
also supports the built-in `io` and `math` import names and a restricted
`extern "C"` boundary for `Int32`, `Int64`, `Float64`, and `Void` returns.

### Generic-function monomorphization implemented

The repository implements monomorphized generic functions as a v0.2 feature.
Generic declarations carry distinct type-parameter identities, and the typed
program records concrete type arguments and specialized call signatures. Calls
may provide explicit type arguments or infer them from argument types when
every parameter has one unambiguous concrete substitution. The compiler emits
only used specializations, reuses an existing specialization for repeat calls,
and names specializations deterministically. Same-type generic recursion works.
Recursion that keeps expanding a type, or a program requiring more than 512
specializations, receives a diagnostic rather than looping indefinitely.
Inference uses call arguments, not an expected result type; an unconstrained
parameter therefore requires an explicit argument (or produces an inference
diagnostic).

Native generic functions currently support concrete primitives, class and
struct values/references, and nested built-in `List<T>` types. Generic user
classes and structs remain frontend-only: the parser and semantic analyzer
recognize their declarations, type references, arity, fields, and recursively
invalid inline struct layouts, but LLVM layout and native construction for
those instantiated user-defined types are not implemented. `List<T>` keeps
its existing native runtime representation. This is partial v0.2 progress, not
a claim that the full generic, interface, trait, or enum scope below is
complete.

The compiler pipeline and managed-memory behavior are documented in
[`v0.1-scope.md`](v0.1-scope.md). In particular, v0.1 managed storage is
retained for the process lifetime and released when the generated program
exits; it is not a tracing garbage collector.

## v0.2 additions

### General generics and specialization

Generalize type parameter syntax across functions, methods, classes, structs,
and enums. Type arguments may be nested, so types such as `List<Box<Int>>` are
expressible. The existing `List<T>` syntax and behavior remain supported.

```princi
fn identity<T>(value: T) -> T {
    return value
}

struct Box<T> {
    value: T
}

enum Option<T> {
    Some(T),
    None
}
```

Generic function arguments are inferred when call arguments determine one
unambiguous substitution; callers may write explicit type arguments when
inference is insufficient. Generic class, struct, and enum arguments are
specified at type use and construction sites. The compiler specializes generic
code at compile time (monomorphization) for each concrete type-argument set.
There is no runtime generic reflection or user-controlled specialization
syntax. Generic function specialization is implemented for the concrete types
listed above; generic methods and instantiated user-defined classes/structs
remain planned work.

### Generic constraints

Generic parameters may declare one or more trait bounds inline:

```princi
fn describe<T: Display + Debug>(value: T) -> String {
    return value.toString()
}

struct Box<T: Display> {
    value: T
}
```

Bounds are checked statically before specialization. For v0.2, generic
constraints are trait bounds; interfaces are runtime-dispatched class contracts
and are not generic bounds. Bounds do not add automatic conversions, and the
compiler reports a diagnostic when a concrete type does not satisfy a required
trait. Trait definitions themselves are not generic in v0.2.

### Interfaces and runtime dispatch

An interface declares a set of instance-method signatures. It has no stored
fields, constructors, default method bodies, associated types, or generic
methods. Classes explicitly declare the interfaces they implement and must
provide compatible methods. A class may implement more than one interface.

```princi
interface Printable {
    fn text() -> String
}

class User implements Printable {
    name: String

    init(name: String) {
        self.name = name
    }

    fn text() -> String {
        return self.name
    }
}

fn show(value: Printable) {
    println(value.text())
}
```

In v0.2, only class instances can be stored as interface-typed values. Assigning
or passing a conforming class to an interface-typed destination creates the
interface view; calls through that view use compiler-generated interface
dispatch metadata. Calls on a concrete class keep v0.1 static dispatch. Structs
do not convert to interface values in v0.2. Interfaces are not a class
inheritance mechanism.

### Traits and trait implementations

Traits describe compile-time capabilities. A trait may require instance methods
and provide default method bodies. An explicit implementation supplies any
required methods that do not have defaults:

```princi
trait Describable {
    fn description() -> String

    fn printDescription() {
        println(self.description())
    }
}

impl Describable for Point {
    fn description() -> String {
        return "Point"
    }
}
```

Trait implementations are allowed for concrete classes and structs. A generic
function or type can call methods provided by its trait bounds; those calls use
static dispatch and are resolved during specialization. Default methods are
made available through the implementation. Traits do not produce
interface-typed values or runtime trait objects. Trait definitions are
non-generic; associated types, blanket implementations, overlapping
implementations, and specialization rules are outside this version.

### Algebraic enums and pattern matching

Enums add named variants with optional positional payloads. Enums may be
generic. Their runtime representation is compiler-selected tagged storage; the
source language has no representation or layout attributes.

```princi
enum Option<T> {
    Some(T),
    None
}

fn valueOrZero(value: Option<Int>) -> Int {
    return match value {
        Option<Int>::Some(number) => number,
        Option<Int>::None => 0
    }
}
```

`match` is an expression. V0.2 patterns support enum variants, recursively
destructured payloads, variable bindings, and `_` as a wildcard. Every arm must
produce the same type. A match must cover every possible variant; a wildcard
can cover otherwise-unmatched variants. Match guards, integer/range patterns,
and destructuring of classes, structs, or lists are not included.

### `Result<T, E>` and `?`

`Result<T, E>` is a predeclared generic enum with `Ok(T)` and `Err(E)` variants.
It uses the same enum, construction, and matching rules as user-declared enums.
The postfix `?` operator propagates an error from a `Result` expression:

```princi
fn readValue() -> Result<Int, String> {
    let value = parseInteger("42")?
    return Result<Int, String>::Ok(value)
}
```

The containing function must return `Result<T, E>`, and the operand must have
type `Result<U, E>` with the same error type `E`. `?` unwraps `Ok(U)` to `U`
and returns `Err(E)` from the current function. There is no implicit error
conversion. The process entry point remains `fn main() -> Void` or `fn main() ->
Int`; `?` does not change the executable entry-point contract.

## v0.2 compiler architecture

The v0.1 frontend and Windows native pipeline remain the foundation. The
planned v0.2 stages add generic constraint checking, interface/trait
conformance checking, match exhaustiveness analysis, and generic specialization
before LLVM lowering:

```text
.prnc / .princi
        ↓
      source
        ↓
      lexer
        ↓
      parser
        ↓
       AST
        ↓
 built-in module resolution
        ↓
 semantic and type analysis
 (bounds, implementations, exhaustiveness)
        ↓
 generic specialization
        ↓
 typed representation
        ↓
     LLVM IR
        ↓
 Windows x86-64 COFF object
        ↓
 MinGW-w64 linker and runtime
        ↓
       .exe
```

Generic specializations are compile-time artifacts. Enum tags/payloads and
interface dispatch tables are compiler-managed implementation details, not
user-defined layouts. Existing strings, classes, lists, and other managed
references continue to use the private runtime allocation boundary. This scope
does not require changing the v0.1 process-lifetime allocation model.

The existing Rust implementation is split across these modules:

| Concern | v0.1 implementation |
| --- | --- |
| CLI and build configuration | `src/cli.rs`, `src/compiler/options.rs`, and `src/compiler/pipeline.rs` |
| Source locations and diagnostics | `src/source.rs` and `src/diagnostics.rs` |
| Frontend | `src/lexer.rs`, `src/parser.rs`, and `src/ast.rs` |
| Imports and C ABI boundary | `src/modules.rs` and `src/ffi.rs` |
| Semantic analysis and types | `src/semantic.rs` and `src/types.rs` |
| LLVM generation and native toolchain | `src/codegen/llvm.rs` |
| Runtime ABI | `src/runtime.rs` and `src/runtime/windows_x86_64.rs` |

The v0.1-compatible type model distinguishes concrete primitive, class, and
struct types, generic type parameters, and generic instances. `List<T>` is the
only generic instance with complete v0.1 native support; the repository's
initial generic frontend work is documented above. Class instances are managed
references with an internal metadata pointer followed by fields in declaration
order. Structs are LLVM aggregates copied by value. Lists are opaque managed
references with homogeneous element storage. Imports resolve only the built-in
`io` and `math` names, and `extern "C"` accepts only the documented primitive
ABI types.

## Compatibility expectations

- Every v0.1 language feature and its behavior remain supported; the existing
  v0.1 conformance and native integration programs must continue to compile and
  run with the same observable results.
- `.prnc` and `.princi` remain exact aliases. Neither extension may select a
  different parser, type rule, or backend path.
- The user-facing workflow remains `princi build <source-file>` with optional
  `-o <output.exe>`. There are no new top-level CLI commands in v0.2.
- Windows x86-64 remains the only target. The object format, linker pipeline,
  and toolchain diagnostics remain Windows-specific.
- Existing numeric rules, class reference behavior, struct value behavior,
  List behavior, module registry, C FFI boundary, and managed-memory model do
  not change as a side effect of adding the listed features.
- New syntax words should be contextual so existing v0.1 identifiers remain
  usable. The built-in `Result<T, E>` is selected by its two generic arguments;
  an existing unparameterized user type named `Result` must keep its meaning.
- New errors remain source-positioned compiler diagnostics and failures return
  a non-zero exit code without exposing internal panics.

## Explicitly outside v0.2

These are not v0.2 features. Listing them here marks the boundary, not a release
commitment or a promise that they are the next roadmap items:

- Class inheritance, virtual class inheritance, and virtual class methods.
- Raw pointers, unsafe blocks, manual memory management, ownership/borrowing,
  and user-controlled arenas.
- Async/await and threading language syntax.
- Package management and remote dependency resolution.
- Linux/macOS compilation and WebAssembly.
- Decorators, reflection, operator overloading, and macros.
- Associated types, higher-kinded types, variadic generics, user-defined
  specialization syntax, and user-defined memory layouts.

## Future functionality

Anything beyond the v0.2 additions above remains future work. Potential areas
for later design include broader platform support, richer runtime memory
management, package/module ecosystems, and additional generic abstractions.
None of those capabilities should be described as available until they are
implemented, tested, and documented against the compiler.
