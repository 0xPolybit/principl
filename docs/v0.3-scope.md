# PrinciPL v0.3 scope

> **Status:** planned scope, not implemented. PrinciPL v0.2.0 remains the
> current release. This document records the intended v0.3 boundary; it is not
> a delivery date or a claim that the features below are available.

PrinciPL v0.3 is planned around four connected areas: asynchronous
programming, structured concurrency, safe use of OS threads, and project/module
tooling. The goal is to make concurrent programs and multi-file projects
practical without weakening the language's current static checks or pretending
that v0.2 already has these capabilities.

## Release contract

- Keep the target at **Windows x86-64**. No other native target or WebAssembly
  target is in v0.3.
- Preserve existing v0.1 and v0.2 programs wherever practical.
- Preserve the standalone build forms and their behavior:

  ```text
  princi build file.prnc
  princi build file.princi
  princi build file.prnc -o output.exe
  ```

- `.prnc` and `.princi` remain exact aliases for the same language, including
  when used for project modules. If both extensions exist for one resolved
  module name, resolution must report the ambiguity instead of choosing one.
- Project support adds workflows; it does not remove the one-file build
  workflow or silently reinterpret one extension as a different dialect.

## Existing v0.2 baseline

The following are implemented in v0.2 and are retained as the compatibility
baseline, not v0.3 additions:

- Rust compiler frontend with source spans, lexer, parser, AST, diagnostics,
  semantic analysis, and typed representation.
- `Int`, `Float`, `Bool`, `String`, `Void`, functions, local variables,
  assignment, expressions, branches, loops, and recursion.
- Classes, structs, `List<T>`, interfaces, traits with default methods,
  generic functions/classes/structs/enums, bounds, and monomorphization.
- Algebraic enums, payload patterns, match expressions, exhaustiveness
  checking, `Result<T, E>`, and `?` propagation.
- Built-in `io` and `math` import names and the restricted primitive C FFI.
- LLVM IR generation, Windows x86-64 COFF output, MinGW-w64 linking, and the
  platform runtime.
- Process-lifetime managed allocations released at program termination. This
  is not tracing garbage collection.
- A single user-facing command, `princi build <source> [-o output.exe]`.

The current import resolver does not load user source files or packages. The
current parser, semantic analyzer, and runtime do not provide async execution,
threads, channels, mutexes, or atomics. See [`v0.2-scope.md`](v0.2-scope.md)
for the complete current language contract.

## 1. Asynchronous programming

The parser's v0.3 syntax foundation uses `async fn` for top-level async
functions, prefix `await` and `spawn` expressions, `scope { ... }` for a task
scope, and `thread spawn function(args)` as the reserved OS-thread form.
`await` binds at unary precedence and is accepted only inside an async
function. Async methods are not part of this initial syntax foundation. These
forms currently produce AST nodes only; runtime behavior and LLVM lowering are
not implemented in the v0.2 compiler.

### Planned surface

```princi
async fn fetchName() -> String {
    await sleep(100)
    return "Princi"
}

async fn main() {
    let name = await fetchName()
    println(name)
}
```

The v0.3 design is:

- An `async fn` declares its eventual value type as its return type. Calling it
  creates a `Task<T>`; it does not execute the body synchronously to produce
  `T`.
- `await task` is a prefix operation accepted only in an async function.
  Awaiting `Task<T>` yields its completed `T` value or propagates a task-level
  cancellation/failure to the awaiting task.
- `Task<T>` is a compiler/runtime-managed handle, not a raw pointer or a
  user-implemented generic class. It cannot be manually allocated or freed.
- `async fn main()` is supported through a native startup wrapper that starts
  the async runtime, awaits the entry task, performs runtime shutdown, and
  returns the program's normal exit status.
- `spawn` schedules an async call as a child of the active task scope. Detached
  tasks are not part of v0.3.
- `cancel(task)` requests cooperative cancellation of a child in the current
  scope; it does not forcibly stop executing code.
- Async sleep/timers suspend a task without blocking the executor thread.
  The initial `sleep(milliseconds: Int)` API uses non-negative milliseconds
  and a monotonic clock.
- Cancellation is cooperative. Cancellation is observed at suspension points
  and runtime waits; v0.3 does not forcibly terminate a running task or OS
  thread.

Async tasks run on the Princi async runtime and may share ordinary managed
values, including classes, strings, and lists. The initial executor is
cooperative and single-threaded: tasks can interleave at suspension points, but
they do not concurrently mutate values on separate OS threads. This prevents
data races; it does not prevent logical races caused by interleaving.

## 2. Structured concurrency

Every spawned async task belongs to a lexical task scope. A proposed source
form is:

```princi
async fn main() {
    scope {
        let child = spawn fetchName()
        let name = await child
        println(name)
    }
}
```

The v0.3 guarantees are:

- A task cannot outlive the scope that spawned it. There is no detached-task
  escape hatch.
- Normal scope exit waits for every child that has not already been awaited.
- Parent cancellation requests cancellation of its outstanding children and
  waits for their termination before the parent scope finishes.
- A task-level failure is never silently discarded. A child failure cancels
  its siblings and propagates to the parent scope. An `Err` value carried by
  `Result<T, E>` remains an ordinary language value; it is not implicitly
  treated as a task failure.
- Cancellation and task failure remain distinct from Princi's existing
  `Result<T, E>` values. The runtime API must make task completion, failure,
  and cancellation observable without adding exception syntax or implicit
  error conversions.
- Scope exit and joining are deterministic from the program's perspective;
  the language does not promise a particular order among concurrently
  runnable children.

These spellings are the current syntax design; the lifetime and failure
guarantees above are required for v0.3.

## 3. OS threads and synchronization

v0.3 adds explicit OS-thread handles and synchronization primitives. These are
separate from async `Task<T>`: awaiting a task is not the same operation as
joining a thread.

Planned runtime types and operations include:

- `Thread<T>` handles for starting a named Princi function on an OS thread and
  joining it to obtain its result.
- `Channel<T>`, `Sender<T>`, and `Receiver<T>` for message passing. Send and
  receive operations have documented blocking and close behavior.
- `Mutex<T>` for synchronized shared mutation. Access to its protected value
  must be scoped so an unlocked mutable reference cannot escape.
- A deliberately small atomic set, initially integer and boolean atomics,
  with a conservative, documented memory-ordering policy.

### Thread-transfer rules

Princi v0.3 has no ownership or borrow checker, so OS-thread transfer cannot
rely on developers promising not to alias mutable values. The compiler must
apply conservative, structural thread-safety rules:

- Primitive values and immutable `String` values may cross thread boundaries.
- Structs and enums may cross when every contained value satisfies the same
  transfer rule. Generic arguments must satisfy the relevant bound at
  specialization time.
- Mutable managed references such as class instances and `List<T>`, plus
  interface/trait values that may hide them, are not transferable or shareable
  across OS threads by default.
- A mutable value may be shared across threads only through the synchronized
  `Mutex<T>` API. The API must prevent its protected mutable reference from
  escaping the lock scope.
- `Channel<T>` accepts only values that satisfy the compiler's thread-transfer
  rule. The compiler derives these capabilities; v0.3 does not allow user code
  to assert an unsafe `Send`/`Sync` implementation.
- Thread entry uses named functions and explicit arguments. General closures,
  arbitrary managed-reference capture, and detached threads are not introduced
  as shortcuts around these rules.

Async tasks may share normal managed values within the async runtime as
described above. The stricter transfer/share checks apply at OS-thread
boundaries. Runtime allocation bookkeeping and synchronization must themselves
be safe when multiple OS threads use permitted runtime values.

## 4. Projects, modules, and package tooling

### Project shape and manifest

The planned project root contains a `princi.toml` manifest and a source tree,
for example:

```text
hello-project/
  princi.toml
  princi.lock
  src/
    main.prnc
    geometry.princi
```

`princi.toml` declares package metadata, the project entry source, and
dependencies. `.prnc` and `.princi` files can be mixed in one project. A source
module name resolves deterministically beneath the project source root. The
resolver rejects traversal outside permitted roots, duplicate module loads,
ambiguous extension aliases, and cyclic module graphs with diagnostics.

### Modules and visibility

- User-defined imports load local project modules. The existing built-in
  `io` and `math` names remain available and cannot be shadowed by project
  modules.
- Module identity is based on the resolved project-relative module path, not
  the spelling of its source extension.
- Top-level declarations are private to their module by default. An explicit
  `pub` marker exposes a supported declaration to importing modules. Private
  names cannot be imported or referenced from another module.
- Modules are compiled as one project dependency graph, with each module
  parsed and semantically analyzed once. Cycles are diagnosed; repeated
  imports reuse the already resolved module.
- The current single-file build remains supported even when no manifest is
  present. Project mode adds manifest-aware module resolution without
  changing that path.

### Dependencies and deterministic builds

- v0.3 supports local path dependencies and Git dependencies. Remote package
  registries, publishing, and version-range solving are not part of this
  scope.
- Local path dependencies are declared explicitly and resolved relative to the
  declaring manifest. Their package roots and module graphs are validated
  before compilation.
- Git dependencies are pinned to immutable commit IDs in `princi.lock`.
  A manifest may name a tag or branch for convenience, but only an explicit
  dependency-resolution/update operation may move that reference. It records
  the selected full commit ID in the lockfile; ordinary builds use that locked
  commit and never update dependencies implicitly.
- `princi.lock` records the complete dependency graph and exact Git revisions.
  A locked build must not silently update dependencies.
- A project build without a lockfile fails with an instruction to resolve
  dependencies explicitly; it does not perform an implicit network update.
- The package cache is local and keyed by canonical source identity and
  resolved revision. Cache contents do not change dependency selection.
- Dependency/module resolution order is deterministic and duplicate or
  conflicting package identities produce actionable diagnostics.

### Planned CLI shape

The source-file workflow stays exact. Project support is additive and is
planned to use project-aware forms such as:

```text
princi init [path]
princi build <file.prnc|file.princi> [-o output.exe]
princi build [project-directory]
princi check [project-directory]
princi add <name> --path <directory>
princi add <name> --git <url> (--rev <commit> | --tag <tag> | --branch <branch>)
princi update
```

These commands describe the intended v0.3 workflow; implementation must define
argument disambiguation so a source file continues to select the existing
single-file build. No package download, lockfile update, or other write should
be hidden behind a bare source-file build. Remote Git fetching is explicit and
limited to dependencies declared by a project.

## Managed-memory boundary and future versions

The v0.3 concurrency work does not replace v0.2's automatic process-lifetime
managed allocation. Allocations still remain valid until program shutdown and
are released then. v0.3 may make the allocator registry thread-safe and add
runtime synchronization needed by `Mutex`, channels, and threads, but it does
not add collection or user-controlled lifetimes.

Memory-system work is deferred beyond v0.3. These are exploratory directions,
not promises or scheduled releases:

- **v0.4 research:** evaluate deterministic/owned lifetimes, scoped arenas,
  and any limited borrowing model. No design should imply that Rust-style
  ownership or borrow checking is already part of v0.3.
- **v0.5 research:** evaluate tracing or concurrent collection and whether
  lower-level raw/manual memory, unsafe blocks, or user-defined destructors
  can be added without compromising ordinary safe Princi code.
- The order and eventual contents of these releases remain subject to separate
  design and compatibility review. Raw pointers, `unsafe`, `alloc`/`free`,
  arenas, ownership/borrowing, destructors, and tracing/concurrent GC are all
  excluded from v0.3.

## Explicitly outside v0.3

- Raw pointers, unsafe blocks, manual `alloc`/`free`, borrow checking,
  Rust-style ownership, user-controlled arenas, user-defined destructors, and
  tracing or concurrent garbage collection.
- Class inheritance, macros, reflection, and operator overloading.
- Linux/macOS native compilation, WebAssembly, and GPU programming.
- Public package registries, dependency publishing, and unrestricted remote
  dependency resolution.

## Compatibility and acceptance expectations

- The complete v0.1/v0.2 conformance suite continues to pass unchanged.
- Standalone `.prnc` and `.princi` files compile identically with the current
  `princi build` command and optional `-o` path.
- Async tasks have structured lifetimes, cooperative cancellation, and
  observable failure; no child task is silently detached or abandoned.
- OS-thread APIs reject values that could expose unsynchronized mutable
  managed state. Channel payloads and thread parameters follow the same
  conservative transfer checks.
- Project builds resolve modules and dependencies deterministically from the
  manifest and lockfile. An unchanged lockfile selects unchanged dependency
  revisions.
- Compiler and runtime diagnostics remain source-positioned where the source
  is responsible, and package/toolchain failures remain actionable.
- Native compilation continues to target Windows x86-64 only.
